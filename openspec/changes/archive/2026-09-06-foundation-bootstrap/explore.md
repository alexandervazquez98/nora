## Approaches

### Fork 1 — Python interpreter pin

| Approach | Description | Pros | Cons | Effort |
|----------|-------------|------|------|--------|
| **Stay on system 3.9.6** | Pin to `python3 == 3.9.6`, install older versions of every dep that still supports 3.9. | Zero install work; no toolchain change. | Every modern NORA dep has dropped 3.9: `fastmcp 4.x` ≥3.10, `google-genai 2.x` ≥3.10, `pysnmp 7.1` ≥3.10, `netmiko 4.x` ≥3.10, `pydantic-settings 2.x` ≥3.10, `zeep 4.x` (transitive of `onvif-zeep`) ≥3.10, `pytest 9.x` ≥3.10. Sticking to 3.9 forces last-generation pins (fastmcp ≤2.x, google-genai ≤1.x, pysnmp 6.x, netmiko 3.x) that approach EOL within the 5-phase roadmap. | Medium (high maintenance debt) |
| **Pin to Python 3.12 via `uv`** | `uv python install 3.12` once; `.python-version` says `3.12`; modern pins for every dep. | All target libs explicitly list 3.12 in their classifiers (verified via PyPI: `fastmcp`, `google-genai`, `pysnmp`, `netmiko`, `pydantic-settings`). Python 3.12 is ~3 years mature by Sep 2026 — perf and typing wins over 3.11, fewer surprises than 3.13 (still settling). Matches NORA's 5-phase roadmap horizon. | One-time `uv` install on a developer machine that has only CommandLineTools Python today. macOS system pip 21.2.4 cannot drive modern installs anyway, so this is not a regression. | Low |
| **Pin to Python 3.11** | Conservative LTS-ish pick. | Same broad support as 3.12, slightly slower, slightly older syntax. | No upside over 3.12 for this stack; pays the same one-time install cost. | Low |

**Recommendation: Python 3.12 (via `uv python install 3.12`, file `.python-version` containing `3.12`).** Justification: every target library lists 3.12 explicitly; 3.12 is mature; the system 3.9.6 is functionally unusable with modern NORA dependencies, and staying would force pinning to last-generation packages throughout the 5-phase roadmap.

### Fork 2 — Dependency manager

| Approach | Pros | Cons | Effort |
|----------|------|------|--------|
| **`uv`** (Astral, Rust, modern) | Lockfile-native (`uv.lock`), 10–100× faster than pip, single tool handles Python version, venv, install, lock, build. Reads `pyproject.toml` PEP 621 directly. First-class `.python-version` integration. Becoming the de-facto default for new Python projects in 2025–2026. | `uv` is not installed yet → one-time `brew install uv` or `curl -LsSf https://astral.sh/uv/install.sh | sh`. Slightly younger ecosystem than poetry (CI integrations, etc.) but improving monthly. | Low |
| **`poetry`** | Mature (2018+), `poetry.lock`, packaging built-in, large community, broad CI plugin support. | Slower resolver; separate toolchain for Python version management (`pyenv`); heavier learning curve; pip compatibility layer is weaker than uv's. Project state-as-of-2026 is "still works, but ecosystem momentum has moved to uv". | Low |
| **`pip + venv + requirements.txt` (with `pip-tools`)** | No extra toolchain. Anyone with Python can run it. | No lockfile by default (need `pip-tools` for `requirements.lock`); manual venv activation; no Python version pin file; doesn't satisfy strict reproducibility that strict TDD + multi-dev roadmap implies. | Medium (long-term maintenance) |

**Recommendation: `uv`.** Justification: it's the only candidate that natively combines Python version pinning, lockfile, venv, and packaging in one tool with PEP 621 `pyproject.toml` support — exactly the surface a 5-phase greenfield project needs in 2026. Poetry is the safe-but-aging alternative; pip+venv is too thin for the review and reproducibility rules in `openspec/config.yaml`.

### Fork 3 — Phase 1 scope split

SCOPE.md §3 Phase 1 deliverables in full: *"Configuración base segura (Pydantic Settings), pipeline de saneamiento/anonimización de telemetría y conector multi-proveedor (LM Studio local + Google Gemini oficial)."*

| Approach | Description | Pros | Cons | Effort | Budget fit (800 lines) |
|----------|-------------|------|------|--------|------------------------|
| **(A) Foundation only** | Repo layout, manifest, pytest+ruff+ty config, Pydantic Settings scaffold, sanitizer stub, one passing FastMCP "hello tool". Multi-LLM in **change #2**. | Smallest change; lowest review risk; no premature interface lock-in. | Phase 1 review would not see any NORA-specific value (no provider, no real tool). Adds a *second* end-to-end change just to deliver Phase 1's stated scope. Drags Phase 1 across two reviews instead of one. | Low | ~450 lines — comfortable |
| **(B) Foundation + multi-LLM connector** | Same as A, plus the `Provider` interface (abstract base class), the `LLMProviderFactory` reading `NORA_LLM_PROVIDER` from Pydantic Settings, one stub `LMStudioProvider` and one stub `GeminiProvider`, and the sanitizer wired to one tool. | Satisfies SCOPE.md §3 Phase 1 end-to-end in **one** change. Provider interface is industry-standard factory/adapter (low lock-in risk). First review sees a real NORA tool talking to a real (mocked) LLM. Phase 1 review surface stays reviewable. | Provider interface commits a method shape (`complete(prompt, context) -> Completion`). If wrong, easy to evolve behind the base class in change #2 — but it is a real commitment. | Medium | ~700 lines — tight but inside 800 |
| **(C) Foundation + multi-LLM + first driver** | B plus a Cambium PTP SNMP driver stub (interface + one no-op implementation). | Gets a Phase 2 head start; more "real" code on day one. | Mixes **two** Phase 1 concerns (multi-LLM, per SCOPE) with a Phase 2 concern (driver layer, SCOPE §4A). Driver interface design is riskier than the LLM one — vendor-specific MIB/OID knowledge leaks easily. Locks two interfaces before Phase 1 review. | High | ~900+ lines — **over budget** |

**Recommendation: (B) — Foundation + multi-LLM connector.** Justification: it matches SCOPE.md §3 Phase 1 deliverables exactly, fits the 800-line review budget (~700 lines), and the provider interface is a low-risk commitment (abstract base class, single method). The "lock-in" risk is real but mitigable: keep the `LLMProvider` base class small, put all vendor details behind it, and reserve the right to evolve the method shape in change #2 if Phase 1 review demands it. Option A undershoots the stated Phase 1 scope; option C exceeds the review budget and tangles Phase 1 with Phase 2 concerns.

## Risks

- **Risk — Python 3.12 install on a CommandLineTools-only machine**: the macOS dev box has no Homebrew `python@3.12` and no pyenv. Mitigation: `uv python install 3.12` installs an isolated interpreter into the uv cache without touching system Python; `.python-version` makes the project self-bootstrap.
- **Risk — LLM provider interface signature chosen before Phase 1 review**: the `complete(prompt, context) -> Completion` shape (or similar) is committed in this change. Mitigation: keep the abstract base class tiny (1–2 methods), and treat change #2 as the natural place to revisit if Gemini multimodal needs shake out a richer interface.
- **Risk — `uv` not on PATH today**: same first-day install story as Homebrew; no blockers. If the human refuses `uv`, fallback is `poetry` (Option B2) — but that requires installing poetry too.
- **Risk — `onvif-zeep` is abandoned (last release 2018)**: it works but pulls `zeep 4.x`, which requires Python ≥3.10 → already satisfied by 3.12. If `zeep` 5.x lands and drops 3.12 support, that breaks only the Phase 2 video driver, not Phase 1. Surfaced here for awareness; does not block this change.
- **Risk — `pytest` CLI script broken in this env**: only `python3 -m pytest` works. Per `openspec/config.yaml` this is already the configured `test_command`; a `Makefile` target will wrap it so contributors don't hit the footgun.
- **Risk — SCOPE.md is in Spanish but artifacts default to English** (per `sdd-explore` Language Domain Contract): resolved by translating any SCOPE-derived comments to English when implementing; SCOPE.md stays untouched.
- **Risk — `.reportes/` contains hand-rolled SNMP code that could "leak" into the foundation**: per `openspec/config.yaml`, `.reportes/` is gitignored and the rule is "port deliberately, do not import." Foundation change creates no imports from `.reportes/`.
